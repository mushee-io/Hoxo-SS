# M15 — Canonical margin ledger, shared reservations and controlled settlement

**Scope:** A new Soroban **single-collateral-token vault** (`contracts/unified-margin`) on Stellar Testnet with canonical free/reserved accounting. This is a real source implementation, **not yet an integrated unified-margin exchange**. No Hoxo contract is deployed; M7 is a preview-only risk gate whose `authorization_enabled()` returns false. M9 spot, M11 lending and M12–M14 perp custody remain isolated and do not invoke this contract.

## Source capabilities

- Constructor requires Testnet network ID, owner authorization and **exactly seven decimals** for the configured collateral token. The new vault starts paused, has no adapters or canonical risk authority, and has no administrative sweep.
- One persistent `Account` per owner: `available_e7` and `reserved_e7` for the same physically held token. `deposit(owner,amount)` credits exactly received tokens; `withdraw(owner,amount)` requires owner signing, and is restricted to **available**, never reserved collateral. Free withdrawals remain possible even while new deposits and reservations are paused.
- One typed `Product` role each for **Spot**, **Perp**, **Lending**. Immutable one-time adapter registration per product, explicit admin activation while paused, and a one-time external on-chain `MarginRisk` authority binding. Enabling new reservations requires `authorization_enabled()==true`; each reservation requires the risk contract's `approve_reservation` for the exact signed amount, asset, owner and product. Existing M7 **cannot satisfy this interface**; tests use mocks only.
- `reserve(owner,adapter,product,id,amount)` requires **both owner and approved adapter authorization**, checks free balance and registered product, risk, positive amount, reservation capacity and token solvency. It moves exact units from `available` to `reserved` on one account without changing aggregate user claims or moving any token.
- Reservation IDs are 32-byte identifiers, immutable across products; `release(id,adapter,amount)` is adapter-signed and moves units back to free balance, even under pause. The owner cannot independently release perpetual liabilities.
- `settle_reserved(id,adapter,recipient,amount)` is adapter-signed, limited to the remaining reservation, and internally moves claims to a recipient's free ledger account. Same-owner settlements are handled separately to prevent double writes. No mint, withdrawal, synthetic borrow, or off-contract token payout occurs. This is accounting infrastructure for *future audited product adapters*; the existing M9, M11 and M12 contracts are **not connected**.
- The global `Totals.user_claims_e7` must never exceed the real Soroban token balance. Transfers between accounts preserve total claims. No user can withdraw another account's reserved or free collateral. Stale/closed reservation IDs are retained as tombstones against replay, subject to TTL/archival recovery.

## Safety and limitations

1. **No actual cross-product transaction bridge yet.** M9 settles two external tokens itself; M12 reserves token escrow inside its own contract; M11 lends from its isolated liquidity pool. Those contracts do not call M15 and therefore **cannot** reuse a single deposit end-to-end. Connecting them requires audited protocol-specific adapters or modifying their canonical custody pathways and enforcing atomic risk reservations.
2. **No real canonical risk authority.** M7 currently evaluates user-supplied previews, not authenticated positions, oracle prices, debt and vault state. Its `authorization_enabled()` returns false and it does not implement `approve_reservation`. M15 can only be activated against a separately reviewed and deployed compliant authority.
3. **Single 7-decimal collateral token**, without oracle haircuts, multi-currency FX or cross-token netting. Reserved amounts cannot create leverage; they are strictly bounded by actually held free collateral. Interest and loan principal are not counted as liquid margin.
4. **Trust in adapters and admin:** A configured adapter can transfer **only its own previously reserved funds** to another account, but a malicious adapter could misdirect those locked claims. Admin risk/adapter addresses require external code-hash verification, governance, and audit. There is no audited upgrade, emergency adapter replacement or forced release process yet.
5. **Soroban TTL archival:** persistent account and reservation keys must be renewed and restored; expired tombstones could permit replay until archival restoration is handled. The permissionless `keepalive(owner,id)` only extends keys that still exist. Do not expose deposit UI or accept public funds before monitoring/restore runbook and audit.
6. **No verified deployment or real money:** all registry roles, including `unified-margin`, remain `planned`, with null IDs and no Testnet signatures/receipts. Trading, custody, lending, liquidation and wallet execution stay disabled in the website.

## Verification

Use `cargo test -p hoxo-unified-margin --lib` and `stellar contract build --package hoxo-unified-margin` with the official Stellar CLI. GitHub CI adds native Soroban tests covering cross-product oversubscription, replay, auth failures, risk denial, wrong network, role governance, paused withdrawals, double-entry settlement, token solvency and TTL renewals. These mock-controller tests do not establish operational adapter readiness.

**M15 acceptance is staged:** a canonical, tested single-token account/reservation foundation is implemented; true spot/perp/lending risk-netted execution and deployment remain incomplete until linked product adapters, canonical oracle risk, signed receipts and external audit are verified.
